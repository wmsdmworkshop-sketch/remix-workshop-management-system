# DWIP Operational Event Engine Implementation Report (Milestone M1)

This report details the architectural audit, design decisions, and implementation details for the CR-002 Event Engine.

---

## 1. Architectural Audit

In compliance with the architectural conditions, we conducted an audit of the existing WMS database tables and services to determine if they can serve as the Operational Event Store without introducing a new table (`tbl_operational_events`).

### Evaluation of Existing Components:

1.  **`tbl_workflow_history`**:
    *   *Current Role*: Logs state transitions during the 12-state workflow machine execution.
    *   *Feasibility as Event Store*: Highly feasible. It is already an append-only log structured around vehicle job IDs.
    *   *Required Extension*: We can add columns for metadata, category, event status, event version, sequence numbering, correlation/parent relationships, actor roles, source systems, and payload objects.
2.  **`tbl_audit_trail`**:
    *   *Current Role*: Logs system audits (action codes and diff payloads) for administrative and security compliance.
    *   *Feasibility as Event Store*: Poor. It lacks index structures and schemas optimized for operational queries and sequence ordering.
3.  **`tbl_notifications` (WOS_TIMELINE_RECORD hack)**:
    *   *Current Role*: Used as a temporary timeline log by serializing logs into notification payloads.
    *   *Feasibility as Event Store*: Poor. Storing core operational history in notification records mixes concerns and leads to high database bloat and performance degradation on notification queues.

### Decision: Extended Unified Event Store
Instead of creating `tbl_operational_events`, we have **extended `tbl_workflow_history`** to act as the unified Operational Event Store. By adding the necessary fields directly to `tbl_workflow_history` and providing proper default values, we preserve backwards compatibility, reuse the existing database model, and satisfy all CR-002 requirements.

To support the extended unified Event Store, the `tbl_workflow_history` table is extended with the following columns in [src/db/schema.ts](file:///c:/Users/arhaa/.gemini/antigravity-ide/scratch/remix-workshop-management-system/src/db/schema.ts):

| `payload` | TEXT | Extra metadata payload in JSON. |

## 3. Read-Only Replay Engine Design

To satisfy condition 3, the `ReplayEngine` operates in a strictly **read-only** manner.
*   **Timeline Reconstruction**: Replay parses chronological events in `tbl_workflow_history` for a given Job Card and projects the final state and calculated TAT values in memory.
*   **No Database Modification**: Replay queries never issue `UPDATE` or `INSERT` statements to the `job_cards` table or any other transactional tables.

---

## 4. Operational Event Categories

Events are classified into six distinct categories:

1.  **Operational**: Core state transitions and floor status changes (`VEHICLE_GATE_IN`, `WIP_STARTED`, etc.).
2.  **Integration**: Events syncing state with external systems like Oracle Siebel (`ESTIMATE_SYNCED`, `INVOICE_IMPORTED`).
3.  **System**: Auto-triggered actions (`SLA_BREACHED`, `TIMER_EXPIRED`).
4.  **AI**: Recommendations generated by intelligence engines (`AI_RECOMMENDATION_MADE`, `DECISION_OVERRIDDEN`).
5.  **CCTV**: Automated license plate scans at entry/exit gates (`CCTV_PLATE_CAPTURED`).
6.  **Mobile**: Direct actions initiated by technicians or supervisors via handheld devices (`TECH_CHECKIN`, `CHECKLIST_SUBMITTED`).
